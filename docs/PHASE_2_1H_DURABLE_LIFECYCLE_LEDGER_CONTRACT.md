# Phil AI OS Platform — Phase 2.1H Durable Lifecycle Ledger Contract

**Status:** DESIGN CONTRACT — NO PRODUCTION MUTATION AUTHORIZED  
**Date:** 2026-08-27

## Decision

Phase 2.1H adopts an append-only lifecycle event ledger as the preferred persistence model for new canonical tasks. Existing approval and execution tables remain authoritative for approval semantics and execution audit; they are not overloaded with inferred lifecycle columns.

## Proposed table

`task_lifecycle_events`

Minimal non-secret columns:

- `event_id` — opaque immutable identifier, e.g. `evt_<uuid4>`
- `task_id` — canonical immutable task identifier
- `stage` — lifecycle stage enum/value
- `occurred_at` — UTC timestamp generated by the authoritative writer
- `source_component` — component that emitted the event
- `actor_id` — authoritative actor/agent identifier when known, nullable
- `assigned_agent_id` — authoritative assigned agent when the event itself proves assignment, nullable
- `previous_stage` — previous durable stage when known, nullable
- `reason_code` — bounded non-secret machine-readable reason, nullable
- `correlation_id` — existing approval/execution identifier when useful, nullable

The table must not store task text, decision notes, link hashes, provider responses, prompt payloads, credentials, bearer tokens, or secret material.

## Append-only invariants

1. Lifecycle events are inserted, never updated in place.
2. `event_id` is immutable and unique.
3. `task_id` is immutable and must already exist as a canonical task identity.
4. Historical approval/execution rows are not backfilled with invented lifecycle events.
5. Repeated stages are permitted only when they represent distinct durable events and remain auditable.
6. Deleting lifecycle events is prohibited during normal operation; retention/archival requires a separate governance gate.

## Assignment semantics

`assigned_agent_id` is descriptive operational ownership only. It is not an authorization token and cannot:

- increase authority level;
- widen allowed task classes;
- bypass human approval;
- bypass execution allowlists or kill switch;
- change provider routing;
- confer permission to self-approve.

A handoff is represented by a new append-only `ASSIGNED` event for the same `task_id`, optionally with `previous_stage`/reason metadata. The handoff must remain within the receiving agent's already-declared authority boundary.

## Authoritative writers

Initial writer ownership should remain inside the Control API boundary for lifecycle events tied directly to existing durable functions. Mission Control/browser is never a lifecycle writer in Phase 2.1H.

Safe future writer mapping:

- `RECEIVED` — Control API at canonical approval/task creation
- `CLASSIFIED` — Control API only when classification result is actually finalized
- `APPROVAL_PENDING` — Control API after durable approval creation in pending state
- `AUTHORIZED` / `DENIED` / `EXPIRED` — Control API at authoritative approval transition
- `ASSIGNED` — only an explicit future assignment function/service; never inferred from requester/source/consumer fields
- `POLICY_CHECK` — only when a durable policy evaluation actually executes and returns a result
- `EXECUTING` — execution boundary immediately before provider execution begins, if such a start point can be made durable without creating false positives
- `SUCCEEDED` / `FAILED` / `BLOCKED` / `CANCELLED` — execution boundary after authoritative outcome
- `AUDITED` — after execution audit persistence succeeds
- `CLOSED` — only a future coordinator/operator workflow that explicitly closes the task; never inferred from success alone

## State-machine policy

The canonical lifecycle contract remains:

`RECEIVED -> CLASSIFIED -> ASSIGNED -> PLANNED -> POLICY_CHECK -> [APPROVAL_PENDING] -> AUTHORIZED -> EXECUTING -> {SUCCEEDED | FAILED | BLOCKED | CANCELLED} -> AUDITED -> CLOSED`

Exception states include `DENIED`, `EXPIRED`, `REJECTED`, `AMBIGUOUS`, and `CONTAINED`.

The ledger records events; it does not itself grant transition authority. Transition validity is a separate policy function.

## Backward compatibility

- Existing 45 approval and 34 execution-audit legacy rows remain unchanged.
- Existing `approval_id` and canonical `task_id` contracts remain immutable.
- Legacy records without lifecycle events remain valid and are labeled partial/legacy by Mission Control.
- New lifecycle persistence must be nullable/additive from the perspective of existing read and execution paths.

## Proposed indexes

- unique index on `event_id`
- index on `(task_id, occurred_at, event_id)`
- optional index on `(assigned_agent_id, occurred_at)` only if assignment queries become necessary

## Rollback contract

Before any production activation:

1. validate migration on a copied live DB;
2. prove legacy row counts and contents remain unchanged;
3. prove append-only inserts and indexes work;
4. validate Control API candidate against copied DB/state;
5. back up production SQLite and Compose/image state;
6. recreate only Control API if application code changes;
7. rollback both DB and service/image on any failed invariant;
8. verify Mission Control remains read-only and production allowlist remains exactly `general`.

## Current authority decision

This document approves design and isolated validation only. It does not authorize production schema creation, lifecycle event writes, agent assignment writes, or any authority expansion.
