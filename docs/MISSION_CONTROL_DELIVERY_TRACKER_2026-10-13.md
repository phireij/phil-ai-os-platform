## Progress monitoring and update rules

1. Update this file after each **verified milestone or material blocker**, recording date/time, evidence reference, and schedule status. Keep brief implementation notes in the append-only log below.
2. Status vocabulary: **ON TRACK** (evidence supports deadline), **AT RISK** (critical dependency or estimate threatens it), **BLOCKED** (required external/user action or environment unavailable), **DONE** (acceptance evidence complete).
3. When a command or CI/deployment task returns an asynchronous operation/session, record its operation ID and next check time. Recheck after approximately **2 minutes** initially; if unchanged, back off to 5–10 minutes. Never claim completion based on dispatch alone.
4. Raise a user-owned blocker with the precise action, due date, and schedule consequence as soon as it enters the critical path. Continue independent tasks while waiting. If a requested owner date passes, mark the phase at risk/blocked and recalculate immediately.
5. Do not perform a production deployment, merge, provider activation, or authority expansion without its required approval. Never inspect credential files or request that secrets be pasted into chat.
6. Keep Ruby's application development outside this schedule until Mission Control passes its platform gate. Keep Hermes and existing workloads untouched.
