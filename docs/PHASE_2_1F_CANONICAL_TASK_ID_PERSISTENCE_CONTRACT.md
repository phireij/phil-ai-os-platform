# Phase 2.1F — Canonical Task ID Persistence Contract

Status: DESIGN CONTRACT DEFINED / NO PRODUCTION MIGRATION

## Purpose
Introduce a genuine canonical `task_id` that remains stable across approval request, approval decision/consumption, governed execution, execution audit, and Mission Control observability without changing execution authority.

## Discovery evidence
Read-only discovery run `33026405831` completed GREEN with marker:

`PHIL_AI_OS_PHASE_2_1F_WRITE_PATH_DISCOVERY_OK`

Observed durable schemas:

- `approval_requests`: 45 rows; no `task_id` column.
- `execution_audit`: 34 rows; no `task_id` column.
- `approval_requests.approval_id` is the current durable approval key.
- `execution_audit.approval_id` is the current durable approval-to-execution correlation key.

Observed write paths:

- `approval_create()` generates `approval_id`, classifies/routes the request, inserts the approval row, and returns the approval object.
- `approval_consume()` validates `approval_id` + exact `task_text` and atomically consumes the approved request.
- `/v1/execute` requires `approval_id` before governed execution.
- `execution_audit_write()` persists execution audit records and currently accepts `approval_id`.
- Hermes `philaios-execute` sends `approval_id` + task text to `/v1/execute`.
- The Mission Control request client calls `/v1/approvals/request` and does not currently supply a canonical task ID.

## Canonical identity rule
A canonical task ID MUST be generated exactly once by the Control API when a new approval request is accepted.

Recommended format:

`tsk_<uuid4-hex>`

The Control API is the authority for this ID. Browsers, Hermes, specialist agents, and other clients MUST NOT be allowed to choose or override a canonical task ID for a new request.

## Persistence design
### `approval_requests`
Add nullable column:

`task_id TEXT`

For newly created approval rows, `task_id` MUST be non-empty and generated by `approval_create()`.

Add a UNIQUE index on non-null task IDs after compatibility validation.

Historical rows remain NULL initially. They MUST NOT be assigned synthetic task IDs merely to make historical data look canonical.

### `execution_audit`
Add nullable column:

`task_id TEXT`

For governed executions linked to an approval, execution code MUST resolve `task_id` from the authoritative `approval_requests` row identified by `approval_id` and pass that value to `execution_audit_write()`.

A caller-supplied task ID MUST NOT override the value resolved from the approval row.

Historical audit rows remain NULL initially.

## Request / approval contract
`POST /v1/approvals/request`

- Existing request payload remains backward compatible.
- Server generates `task_id` after validation and before durable insertion.
- Response adds `task_id` inside the approval object.
- Existing clients that ignore unknown fields continue working.

## Execution contract
`POST /v1/execute`

- `approval_id` remains required.
- `task_text` compatibility rules remain unchanged.
- Control API resolves the canonical `task_id` from the approval record.
- If the approval row is a historical row with no task ID, execution follows the existing approval governance behavior but audit correlation remains legacy/approval-only unless a separately approved compatibility policy says otherwise.
- A new task ID MUST NOT be generated at execution time for a historical approval.

## Audit contract
`execution_audit_write()` gains optional `task_id=None`.

For new governed approval-backed executions:

- `approval_id` and `task_id` are both persisted.
- `task_id` comes from the approval record.
- Audit failures/rejections that occur before a resolvable approval record may legitimately have `task_id=NULL`.

## Mission Control contract
Mission Control may treat records as canonically task-correlated only when an authoritative non-null `task_id` is present.

Expected hierarchy:

`task_id -> approval_id(s) -> execution_audit row(s)`

The existing `approval_id` durable correlation remains visible and valid during transition.

Mission Control MUST distinguish:

- `canonical` — authoritative `task_id` present and propagated.
- `approval_id_authoritative` — durable approval link present, task ID absent.
- `legacy` — neither canonical task linkage nor complete approval linkage is available.

## Compatibility and migration rules
1. Schema additions are additive and nullable first.
2. No historical backfill in the initial migration.
3. Existing approval IDs remain unchanged.
4. Existing approval consumption semantics remain unchanged.
5. Existing Telegram approval URLs/tokens remain unchanged.
6. Existing `/v1/execute` callers remain compatible.
7. No provider/model/routing changes.
8. Production task allowlist remains exactly `general`.
9. No agent authority level changes.
10. Rollback must restore the previous Control API application and database from a verified backup if migration validation fails.

## Required validation before production activation
A migration candidate is not production-ready until all of the following pass in an isolated database copy or controlled rollback-backed canary:

- SQLite `quick_check=ok` before and after.
- Existing 45 approval and 34 audit rows remain unchanged except additive schema metadata.
- Historical rows retain `task_id=NULL`.
- New test approval receives one server-generated `tsk_...` ID.
- The same task ID is returned by approval reads.
- Approval decision/consumption preserves the task ID.
- Governed execution resolves the ID from the approval row.
- Execution audit stores the same task ID.
- Replay rejection remains effective.
- Approval-to-execution audit linkage remains effective.
- Existing Telegram approval path remains functional.
- Mission Control reads canonical task correlation correctly.
- Browser mutation methods remain unavailable.
- Production allowlist remains `general` only.
- Monitor, backup timer, and backup self-heal remain active.
- No authority expansion occurs.

## Phase 2.1F implementation boundary
Phase 2.1F may prepare and validate the migration and Control API patch, but production activation requires a rollback-backed controlled canary. No widening of execution classes or autonomous authority is part of this phase.
